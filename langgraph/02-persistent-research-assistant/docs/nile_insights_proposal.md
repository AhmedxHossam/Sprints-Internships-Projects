**Subject:** Proposed research assistant: checkpoint memory and research-session isolation

Dear Nile Insights team,

Following our kickoff discussion, we have designed a LangGraph proof of concept for research into Cairo real estate and regional FMCG markets. The assistant separates model reasoning and response generation from a dedicated Tavily search node. This allows it to retrieve external evidence when needed and synthesize findings already collected within the same research thread.

Our memory design distinguishes three concepts. **Scratchpad memory** is temporary working context, such as task notes and intermediate tool observations; placing that context in a prompt does not provide managed persistence. **Window memory** retains a bounded recent portion of the conversation, reducing context size but potentially discarding earlier research constraints or findings. **Checkpoint memory** stores snapshots of graph state at execution steps, including the accumulated messages and tool results. Checkpoints are the appropriate foundation for your workflow because they support continued conversations, inspection of earlier states, and controlled recovery or replay without manually reconstructing a prompt history. Checkpoint storage does not remove the model's context limit; longer projects may subsequently require summarization or selective retrieval.

For this POC, the graph is compiled explicitly with a single `MemorySaver` instance. Each invocation supplies a research identifier through `config={"configurable": {"thread_id": "nile_research_session_1"}}`. Reusing that identifier with the same checkpointer loads the saved state before applying the new user message. A different identifier selects a separate research history, so a Cairo real-estate thread does not automatically acquire the context of a UAE FMCG thread. The included demonstration submits an initial search and then a follow-up without resending the original topic, verifies that the earlier messages and tool evidence remain, and checks a second thread for independent state. Historical snapshots are also retrievable; replaying a prior checkpoint is a separate operation and can execute subsequent model or search calls again.

Secure isolation requires both **thread-scoped state** and **application-enforced access control**. The `thread_id` is a storage selector, not a password, encryption mechanism, or authorization check, and placing it inside `config` does not make it secret. Before any production invocation or checkpoint read, the service must authenticate the analyst and validate that the requested thread belongs to their organization and is accessible under their permissions. The server should generate unique, opaque thread identifiers and maintain ownership records; caller-supplied identifiers must never bypass those checks. API keys remain in environment variables, not in conversation state or source code. The local POC demonstrates state partitioning and does not implement a multi-user authentication service.

There is also an important durability boundary: **`MemorySaver` stores checkpoints in process memory**. It preserves context across invocations only while that process and checkpointer remain available. Closing a browser need not erase state if the backend remains running, but a backend restart loses these in-memory checkpoints. We therefore recommend a database-backed checkpointer, such as `PostgresSaver`, before promising multi-day recovery across restarts or multiple application workers. Production storage should use appropriate access restrictions, transport and storage encryption, and retention controls. Scratchpads and conversation windows can complement this architecture, but neither replaces durable checkpoint storage.

The custom `search_mena_market_data` tool uses the `@tool` decorator, typed input, and a detailed description covering when to search and when to reuse existing evidence. It returns source URLs, excerpts, and publication dates when available. A Gemini model, selected through `GEMINI_MODEL` and connected using `ChatGoogleGenerativeAI`, is bound to this tool. Conditional routing sends tool calls to a distinct `ToolNode` before returning results to the model. This supports source-grounded answers, while source quality, reporting periods, and unsupported claims still require evaluation; tool descriptions cannot guarantee correct routing or eliminate hallucinations. In live mode, search queries are sent to Tavily and model context is sent to Google's Gemini API, so thread separation does not imply that data stays entirely on your infrastructure.

The delivery includes `src/research_agent.py`, `requirements.txt`, this proposal, and a project README. From the project root, running `python src/research_agent.py --mock` uses explicitly fictional search fixtures and a deterministic model simulator without provider API calls. Running with `--mock-search` instead uses the real Gemini model with the same fictional search fixtures, allowing real-model tool selection and thread memory to be checked without a Tavily key. Neither mode validates live retrieval quality. Full live mode requires `GOOGLE_API_KEY` (or `GEMINI_API_KEY`), `GEMINI_MODEL`, and `TAVILY_API_KEY` and is enabled by omitting both flags. Each task has its own private `.env` and `.gitignore`. The script reads only the `.env` at the `nile_insights_project` root, with explicit process environment values taking precedence; it never searches the course root or other tasks. No credential file is included in the submission. No production-grade restart durability or access-control guarantees are claimed for the in-memory POC.
